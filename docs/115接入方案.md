# 115 网盘原生接入 mihonW —— 移植方案

> 目标：在 mihonW（Kotlin / Compose / OkHttp）里原生登录 115 网盘，像现在的 WebDAV 云盘源一样
> 浏览目录、抽封面、流式看 zip/cbz 漫画。
> 现状调研时间：2026-10-05。所有结论均已在本机两份源码上逐一核对（见文末「依据」）。

---

## 0. 结论先行

**可行，而且比预想干净。** mihonW 里 `BaseWebDavSource` 已经是一个"后端无关"的抽象基类，
`WebDavSource`（远端 WebDAV）和 `LocalWebDavSource`（本地文件夹）都是它的子类。
接入 115 = **实现第三个后端**，不需要动阅读器、书架、下载器、封面管线的任何既有逻辑。

- 工作量：**4.5–6 人日**（含真机联调）
- 最大技术难点只有一个：**m115 加密**（取大文件直链必须走它），约 150 行 Kotlin
- 最大不确定项：**115 风控**（405 / 50029 / Cookie 过期），有了 MHW 现成的门控参数可直接照搬

## 3. 115 协议要点（两个项目交叉验证过）

### 3.1 登录：WebView 取 Cookie

- WebView 打开 `https://115.com/`，用户登录后 `CookieManager.getInstance().getCookie("https://115.com")`
- 保留字段：`UID / CID / SEID / KID`（`SEID`/`KID` 是 HttpOnly，但 Android 的 CookieManager 能读到）
- 校验：`GET webapi.115.com/user/info?ct=json`，`errno == 990001` = 登录过期
- `android.webkit.WebView` 是系统 API，**不需要加 Gradle 依赖**，用 `AndroidView { WebView(it) }` 包即可
- 备选 v2：MHW 里还有一套网页二维码登录（`qrcodeapi.115.com` 拿 token → `passportapi` 换 cookie），
  体验更好但链路更长，**建议 v1 先做 WebView**

### 3.2 列目录

```
GET https://webapi.115.com/files
    ?aid=1&cid=<目录id>&o=user_ptime&asc=0
    &offset=<分页>&show_dir=1&limit=100
    &snap=0&natsort=1&record_open_time=1&count_folders=1&format=json
```

- 分页：`offset` 累加到响应 `count` 为止（MHW 用 `WEB_PAGE_SIZE = 200`）
- `natsort=1` 开自然排序；MHW 另有 `aps.115.com/natsort/files.php` 兜底
- ⚠️ **三套 ID 别混**：目录 id 叫 `cid`、文件 id 叫 `fid`、取直链要的是 `pickcode`（列表项的 `pc` 字段）

### 3.3 取直链（大文件唯一通道）

```
POST https://proapi.115.com/app/chrome/downurl?t=<毫秒时间戳>
Cookie: <登录 cookie>
Referer: https://proapi.115.com
body(form): data = m115_encode('{"pickcode":"...","user_id":<UID数字部分>}')
→ 响应 data 是 m115 密文，解密后取 {任一 key}.url.url
```

- **必须走这个加密接口**。网页端 `GET webapi.115.com/files/download?pickcode=` 对大文件直接
  返回 `errno 50028 文件大小超出限制，请使用115电脑端下载`（实测 482MB 就被拒）。漫画 zip 常几百 MB。
- `?t=` **必须放在 URL query 上**（放 body 里会被 WAF 打 405），且要在限流等待**之后**再生成时间戳
- 响应头会下发 **CDN Cookie**，必须与登录 Cookie 合并后一起发，否则 CDN 返回 `403 no cookie value`
- ⚠️ **UA 存在分歧**：YunX 用 `Mozilla/5.0 115Browser/<版本>`（版本过低会 `errno 50029`，
  版本从 `appversion.115.com/1/web/1.0/api/chrome` 动态拉）；MHW 用的是**空 UA** 且实测能通。
  → 实现时**做成可切换开关**，真机上各测一次，取能通的那个

### 3.4 直链缓存与失效重取（关键）

MHW 已经踩完的坑，参数直接照搬：

| 参数 | 值 | 位置 |
|---|---|---|
| 直链缓存 TTL | **300 秒** | `cloud115.rs:1128` |
| API 最小请求间隔 | **1.5 秒**（`RateGate::fixed_interval("115web.api", 1.5)`） | `cloud115.rs:1191` |
| CDN Range 限流 | 独立令牌桶（per_sec / burst / max_in_flight） | `cloud115.rs:1166` |
| WAF 405 冷却 | **60 秒**（命中即全局冷却，不重试） | `cloud115.rs:1130` |
| 403 重取 | 读失败 → 置空缓存 → 重取一次直链 → 重读；再失败才向上抛 | `cloud115.rs:679–727` |

**为什么必须有缓存**：`ArchivePageLoader` 会长时间持有一个 `RandomAccessSource` 并并发解码多页。
若每页都去 `downurl`，一是撞 1.5 秒闸门（翻页卡死），二是极易触发 405 风控。

### 3.5 Range 支持

已验证：**115 直链支持 206 Partial Content**，`bytes=0-0` 可拿到 `Content-Range` 里的总大小。
所以 zip/cbz 可以走 `RemoteZipReader` 直读中央目录 + 按需拉条目 —— 这正是 mihonW 现在对 WebDAV 的做法，
**零额外工作**。

### m115 加密的正确性怎么保证

这是唯一"必须逐字节正确"的模块，写错了整个链路都 403。验证方法：

1. 在 Rust 侧临时加一个测试，对固定输入 `{"pickcode":"test"}` + 固定 16 字节 key 打印密文；
2. Kotlin 侧同样输入跑一遍，**逐字符比对**；
3. 再用固定密文反解，比对明文。

两边都从同一份 MIT 代码来，这个测试只是防止翻译过程中的下标 / 字节序错误。
